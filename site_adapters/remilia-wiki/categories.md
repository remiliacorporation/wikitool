# Remilia Wiki categories

Categories are maintained browsing indexes, not keywords, SEO tags or loose
associations. Ordinary article and template work uses suitable existing
categories; creating, renaming, translating, splitting or merging categories,
changing their scope or hierarchy, or introducing a new membership name belongs
to a separate, explicitly scoped taxonomy effort.

## Articles

Verify the exact live title, definition and representative members, then check
the subject's defining membership against sources. Existing use is not approval:
a populated red-linked category may be a defect. Do not create its description
page merely to make the link blue.

Use the smallest set that provides distinct useful browsing paths. There is no
minimum, target count or default `Category:Remilia`. Do not repeat ancestors,
copy a neighbor's categories or translate category names without checking the
established taxonomy. If none fits, finish the article without categories and
record the gap separately. Diagnostic counts are not editorial obligations.

An NFT collection may fit `Category:NFT Collections` after checking its current
scope. It does not therefore need `NFT projects`, `Blockchain projects`, `Crypto`
and its own project-name category. A trait is not a project: preserve collection
and trait types in structured metadata and existing gallery navigation. Research
any additional browsing index separately.

Membership implying affiliation, ideology, controversy or identity is a factual
claim with source and due-weight requirements. Presence on this wiki proves none
of those relationships.

## Templates and tracking

Maintain a shallow functional template index only where it helps editors find
reusable components. Do not copy an upstream hierarchy or create thematic groups
for every variation. Topic navigation templates should link to topic categories,
not become their members merely because of their subject.

Scope template-only memberships to `noinclude` or documentation. Use
`[[:Category:Name]]` for ordinary links and examples. Before accepting changes,
compare the template's categories and representative caller categories through
the target parser, including relevant parameter branches. HTML-only tests do
not establish category isolation. Arbitrary category parameters do not authorize
new taxonomy.

Automatic caller categories need a reviewed maintenance purpose and scope.
Hide machine tracking categories when useful, but `__HIDDENCAT__` does not prevent
indexing or isolate content. Keep preserved source categories as archive metadata
under the preservation boundary, not native Remilia memberships.

## Taxonomy work

Define the browsing problem and why existing categories, links, lists or metadata
cannot solve it. Inspect the live definitions, complete affected membership lists,
redirects, aliases, language variants and parent graph, recording revisions and
limits. Specify exact names, inclusion/exclusion criteria, useful current members,
parents and treatment of overlaps. A one-article category needs a concrete index
purpose, not hypothetical growth.

Prepare the bounded page and membership changes; check category-tree and
DynamicPageList consumers, template effects, cycles and rollback. Category
redirects alone do not migrate members. Apply only when authorization covers
that production scope, through reviewed Wikitool plans. Category prose still
requires source review; mechanical acceptance is not editorial approval.

Do not expand the tranche opportunistically. Record newly discovered work
separately. This guidance governs agent decisions; `preferred_categories` is a
hint field, not a server restriction or an approved-category allowlist.
